# Whole-product reconstruction contract

The requested objective is an independently implemented replacement for the
whole GMS workbench, with reusable CCS and oil-exploration interfaces. That
objective remains open. Current components include confined groundwater,
general native MF6 execution, bounded conservative-solute transport and partial
GPR tree/geometry readers with explicit views. They do not reduce the definition
of completion.

The reference artifact is the hash-pinned GMS 10.9.7 x64 main executable.
An installer build does not identify an activated edition, all add-ons or
third-party engine rights. Those runtime/dependency facts must be frozen for
each comparison. The 163-entry research catalogue and 576 static command IDs
are finite investigations, not the complete product denominator. The actual
REA ledger keeps a separate whole-product reconciliation barrier open.

## Remaining work by behavior family

| Family | Concrete acceptance work still required |
|---|---|
| Reference environment | Observe normal original startup, edition/module availability, file operations, solver invocation and failure/cancellation behavior; retain exact build and engine identities. |
| Native persistence | Reconstruct actual GPR tree/UUID/package relationships and GUI/native-input synchronization; save/reopen and import/export round trips with quantified losses and unsupported fields. Read-only HDF5 storage is insufficient. |
| Geometry and geology | Cover structured/unstructured geometry, boreholes, sections, horizon contacts, solids, material assignments, mesh construction and refinement; compare coordinates, topology and cell mapping. |
| GIS and acquisition | Verify native GIS/CAD/raster/lidar imports, attributes, coordinate transforms, no-data handling, selection/edit operations and file exports. |
| Interpolation and statistics | Reproduce declared linear/IDW/kriging/geostatistical workflows, anisotropy, sampling and T-PROGS contracts using compatible public components where practical; verify independent small cases. |
| Flow, heat and transport | Complete package-by-package setup, translation, engine execution, outputs and numerical tests for supported MODFLOW families, GWT/GWE, particles, transport and other documented engine interfaces. Engine capability and GUI coverage remain separate. |
| Calibration and uncertainty | Reproduce observations, parameter/pilot-point mapping, PEST/SVD/parallel/transient and uncertainty workflows with exact seeds, bounds, objectives and reference cases. |
| Visualization and interaction | Compare object exploration, editing, data themes, contours, vectors, sections, isosurfaces, clipping, animations, print/export and interaction state. A successful numerical head comparison does not cover these. |
| Operations | Verify malformed inputs, path relocation, missing dependencies, bounded execution, cancellation, diagnostic retention, recovery, edition constraints and repeatable packaging. |
| CCS and oil extensions | Add validated multiphase/black-oil or observation engines behind the shared contract; retain PVT/reference states, component balances and domain-specific evidence. A groundwater project label cannot supply those physics. |

Historical exclusions and geometry-only interfaces are marked in the research
catalogue. Do not implement a historical engine merely because an older manual
mentions it, or attribute the full external engine to a narrower GMS interface.

## Evidence required for a completed capability

1. A stable capability ID, original build/edition/dependencies and an explicit
   scope reconciled with actual menus, dialogs, toolbox tools, formats and
   dynamic operations.
2. Original successful and failure workflows with exact files, actions,
   diagnostics, units, coordinates, datum, time and quantity support. A published
   tutorial output and a newly witnessed original run are different authorities.
3. A concrete original behavior specification, implementation owner and immutable
   source/implementation fingerprint. Unavailable code descriptors are not
   implementations.
4. Independently justified numerical tolerances, physical checks and convergence
   where applicable. Comparisons must share physics, boundary placement,
   discretization and engine versions or explicitly assess their differences.
5. Reproducible reference/candidate fixtures and replayed comparisons, plus
   native-file round trips and interaction tests for the behavior actually
   claimed. Preserve raw outputs; do not hide mismatches with loose tolerances.
6. Explicit incompatibilities, unresolved fields and dependencies. Unknown units
   or stale GUI sidecars must remain unknown instead of being silently repaired.

Full completion requires reconciling the complete runtime inventory and closing
every required capability with appropriate evidence. No percentage of the
current research catalogue or count of decoded resources can substitute for
that requirement. Current genuine GMS runtime output matches remain zero.

## Immediate sequence

Normal original startup, one free Community choice, materialized menus and an
owned standard Open dialog have been observed in separate exact-build runs.
The pinned filename write/readback and Open confirmation then completed, but a
later eight-control dialog was heuristically classified as an error. Cause and
complete project loading are unverified. These observations have not verified
edition entitlement, input translation or numerical execution. A subsequent
passive diagnostic observed licensing/file-operation/error keywords
without establishing a cause or active entitlement. The next reference gate is
independently established MF6 module availability and successful model loading,
followed by captured native inputs/outputs before any numerical equivalence
claim.

For an original numerical comparison, bind the exact project and input graph,
record declared engine/version/units/time/support, retain pre/post file hashes
and fresh diagnostics, then normalize outputs under the existing comparison
contract. A title change or successful process exit cannot replace these gates.
Keep the measured Quadtree Z mismatch and unresolved GUI/native synchronization
visible; do not turn a matching XY footprint into a full model match.

Complete selected native-data contracts, then bind their implementations and
checks into the capability catalogue. Expand the families above in parallel worktrees while preserving
single ownership of each file/branch. The project must continue to publish
working slices and exact remaining gaps without claiming the whole objective
has been completed.


## MF6 run evidence after loading

The exact static resource catalogue does not identify MF6-specific Save/Run
Simulation commands. Its classic MODFLOW command IDs cannot be substituted.
This is a catalogue limitation, not evidence that the product lacks MF6.
The official [MODFLOW6 Grid Approach tutorial, section 14](https://s3.amazonaws.com/gmstutorials-10.9.aquaveo.com/MODFLOW6-GridApproach.pdf)
describes saving and running the simulation from its Project Explorer node,
then using the simulation queue and loading the completed solution. The selected
simulation node and its dynamic context must therefore be observed first.

The pinned GPR already contains a saved Head dataset. Displaying that dataset
does not establish a fresh original run. Before/after input and existing-output
snapshots, selected simulation identity, actual solver image/version, fresh
queue/process/log evidence and output time/shape/budget checks are required.
The saved-native corpus declares feet/seconds and one 86400-second step; GPR
display-time semantics remain unresolved. Use explicit normalized support and
preserve those unknowns in any later comparison.
